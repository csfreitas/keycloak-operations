# Milestone 0.8.1 — Realm & Client Administration

## Status

**IN PROGRESS — Slice 1 implemented; Community Keycloak 26.7.1 integration verified**

Previous completed: **0.8** Controlled Administration & Change Management. Artifact remains `0.8.0-SNAPSHOT` until the full milestone is implemented and accepted.

## Objective

Expand the controlled change lifecycle from the milestone 0.8 proof of concept into typed, semantic realm and client administration without exposing raw Keycloak representations or arbitrary Admin REST mutations.

The first implementation slice is deliberately narrow:

```text
Replace client redirect URI / Web Origin sets
    ↓
Validate and normalize
    ↓
Diff additions and removals
    ↓
Classify risk and evaluate environment policy
    ↓
Approve when required
    ↓
Apply through the stable Admin REST adapter
    ↓
Read back and verify the normalized sets
    ↓
Audit
```

The milestone remains incomplete until all required delivery slices and acceptance criteria below are satisfied. A slice may be merged independently without claiming completion of 0.8.1.

## Delivery slices

### Slice 1 — Client redirect URIs and Web Origins

This slice is implemented in the current working tree. Final acceptance still requires the full validation commands and an explicitly provisioned live integration target.

Required semantic inputs:

```text
targetId
realm
clientId
redirectUris?  complete desired set
webOrigins?    complete desired set
actor?         audit metadata only; not authorization identity
idempotencyKey?
```

At least one of `redirectUris` or `webOrigins` must be present. Omitted fields remain unchanged. An explicitly empty list requests removal of every value in that set.

The public planning contract must be typed. Do not extend the existing scalar `Map<String, Object> desiredState` path to accept arrays.

Suggested MCP surface:

```text
keycloak_plan_update_client_urls
```

Suggested REST surface:

```text
POST /api/v1/changes/plan/client-urls
```

The final names may change during review, but MCP and REST must use the same application service and semantic request model.

### Slice 2 — Client security and flow settings

Candidate typed settings:

```text
pkceCodeChallengeMethod
standardFlowEnabled
implicitFlowEnabled
directAccessGrantsEnabled
serviceAccountsEnabled
publicClient / client-authentication semantics
```

Each setting requires transition-aware risk. Enabling implicit flow or Direct Access Grants, weakening PKCE, or changing client-authentication semantics must not be treated as a generic Boolean update.

### Slice 3 — Client lifecycle

Candidate operations:

```text
create client
enable client
disable client
```

Client creation must use a typed allowlisted request and must not accept or return a secret. Delete and secret rotation remain out of scope.

### Slice 4 — Realm lifecycle and safe configuration

Candidate operations:

```text
create realm
update allowlisted non-sensitive realm settings
enable realm
disable realm
```

The exact property allowlist must be finalized before implementation. Security-sensitive transitions require explicit risk/policy definitions. Complete `RealmRepresentation` payloads and arbitrary attributes are forbidden.

## Slice 1 validation and normalization

Validation must be implemented by deterministic backend code and covered by parameterized tests.

### Common bounds

The implementation must define configurable or documented bounds for maximum entries per field, maximum length per entry, and maximum total request size.

Null entries, blank entries, control characters, malformed URI syntax, fragments where not valid, user-information, and parent-directory path traversal forms must be rejected.

### Redirect URIs

- Prefer absolute `https` URIs and exact matching.
- Loopback HTTP may be supported only through an explicit, tested exception suitable for local/native application development.
- Relative URIs may be supported only when their Keycloak `rootUrl` semantics are explicitly understood, validated, and tested; otherwise reject them in the first slice.
- A full wildcard (`*`) is denied by default, especially for production.
- Partial wildcards require explicit path-only rules and transition-aware policy. Do not invent hostname wildcard semantics.
- URI comparison is case-sensitive where Keycloak uses exact matching. Do not lowercase paths or otherwise change application identifiers.

### Web Origins

- Accept only valid origins or explicitly supported Keycloak sentinel values.
- An origin must not contain user-information, query, fragment, or a non-root path.
- A full wildcard is denied by default for production.
- If the Keycloak `+` sentinel is supported, treat it as a distinct high-impact semantic value and test its effective behavior against supported versions; do not expand it in the caller.

### Canonical collection behavior

After validation, collections must be de-duplicated, deterministically ordered for persistence and fingerprinting, compared as sets for effective-change detection, and preserved without unsafe semantic rewriting.

Reordering alone is not a change. Additions and removals must be visible in the plan. The fingerprint must be stable for equivalent sets regardless of caller order.

## Risk and policy baseline for Slice 1

This table defines the minimum deterministic baseline. Configuration may make policy stricter.

| Effective transition | Minimum risk | Default policy notes |
|----------------------|--------------|----------------------|
| Remove an exact URI/origin | MEDIUM | Can break login or CORS; PRD requires approval |
| Add exact HTTPS redirect URI | MEDIUM | PRD requires approval |
| Add exact HTTPS Web Origin | MEDIUM | PRD requires approval |
| Add approved loopback HTTP URI | MEDIUM | Intended for explicit development/native-client use |
| Add non-loopback HTTP URI/origin | HIGH | Deny in PRD by default |
| Add path wildcard redirect URI | HIGH | Approval required; deny in PRD by default unless policy explicitly permits |
| Add full wildcard | CRITICAL | Deny by default |
| Add Web Origin `+` sentinel | HIGH | Requires supported-version semantics and approval; deny in PRD by default |
| Malformed/ambiguous/unsafe value | N/A | Validation failure; no plan persisted |

When one plan contains multiple transitions, the highest resulting risk wins. The caller cannot supply or downgrade risk.

## Architecture changes

Slice 1 should introduce a cohesive semantic capability rather than one tool per field or a generic mutation endpoint. Expected responsibilities:

```text
Typed request DTO
    ↓
Client URL settings application service/support
    ├── validation and normalization
    ├── set-aware diff
    ├── transition-aware risk input
    ├── safe apply to trusted current representation
    └── read-back verification
    ↓
Existing ChangeManagement lifecycle
    ↓
StableAdminApiAdapter
```

The milestone 0.8 scalar `ChangeOperation.before/after` representation is not sufficient evidence for structured collections unless it gains a canonical structured representation. Do not serialize ad hoc, order-dependent `List.toString()` values into fingerprints. Any evolution of change operation/diff value types must preserve existing 0.8 records and mapper compatibility.

The outbound client update must start from a fresh trusted representation read from the target, apply only allowlisted semantic changes, clear secret/credential material defensively, and preserve unrelated configuration.

## Security

- `targetId` is mandatory and resolved through `TargetRegistry` / `CredentialProvider`.
- Callers never provide Keycloak URLs, credentials, tokens, raw paths, or arbitrary attributes.
- `mcp.read-only=true` continues to allow planning only and block write lifecycle actions according to existing authorization behavior.
- Secrets and credential material must not enter desired state, diff, operations, fingerprints, persistence, responses, logs, or audit.
- Approval remains bound to the exact normalized plan fingerprint.
- Apply must re-read and compare the relevant baseline before mutation.
- Validation, risk, policy, approval, conflict detection, and verification remain backend decisions.

## Persistence and migration

Prefer the existing `change_records` aggregate when it can represent typed collection state safely. Add a Flyway migration only when schema changes are required; do not create an empty version bump.

Existing 0.8 records must remain readable after any mapper/domain evolution. If structured operation values are introduced, include backward-compatibility tests for scalar records.

## Compatibility

The implementation continues to use the stable Keycloak Admin REST boundary through the existing adapter. Current upstream Admin API v2 capabilities are experimental and are not a dependency of this milestone.

Compatibility must be demonstrated separately for the versions actually exercised. A skipped IT is `NOT VERIFIED`, never `TESTED`.

### Unit and component tests

- typed request validation and bounds;
- exact HTTPS values;
- loopback HTTP exception;

- full and partial wildcard rules;

- item-level added/removed diff;

- highest-risk transition wins;
- environment policy decisions;
- approval fingerprint integrity;
- stale baseline conflict;
- preservation of unrelated client configuration;
- secret/credential clearing and leakage tests;
- read-back verification success and mismatch;
- idempotent plan/apply behavior;
- target isolation;
- REST/MCP delegation to the same service;
- compatibility reading existing scalar change records if the domain value model changes.

### Integration tests

Replace or extend the current placeholder with a real opt-in test against a writable Keycloak target:

```text
plan → approve when required → apply → read-back verify → restore test fixture
```

The test must use dedicated disposable realm/client fixtures and must not run against an arbitrary configured target. If it is skipped, report it as skipped.

Run relevant opt-in Keycloak and RHBK tests only with explicitly provisioned disposable targets and credentials.

## Acceptance criteria — Slice 1

Slice 1 is accepted only when:

1. A typed semantic request can plan replacement of redirect URI and/or Web Origin sets for a registered `targetId`, realm, and client.
2. MCP and REST use the same application service; neither accepts arbitrary Keycloak representations or Admin REST input.
3. Validation, bounds, normalization, set-aware diff, risk, and policy are deterministic and covered by tests.
4. Equivalent sets in different orders produce no effective change and stable fingerprints.
5. Full wildcard and unsafe URI/origin cases follow the required deny behavior; production defaults are tested.
6. Apply is blocked by read-only mode, authorization, policy, and approval rules inherited from 0.8.
7. Approval is bound to the normalized plan and stale target state produces conflict/replan rather than overwrite.
8. Apply preserves unrelated client configuration and never sends, persists, returns, fingerprints, or logs secret material.
9. Successful apply performs read-back verification of the normalized desired sets; mismatch is persisted and surfaced as failure.
10. Target isolation, idempotency, REST/MCP behavior, and persisted-record compatibility are tested.
11. `mvn clean verify`, UI tests, and UI build pass; opt-in IT execution or skip status is reported accurately.
12. Requirements, architecture, project state, milestone status, public examples, and known limitations are updated to match implemented behavior.

## Milestone completion criteria

The full 0.8.1 milestone may be marked **COMPLETED** only after:

- Slice 1 is accepted;
- the final agreed scope for Slices 2–4 is implemented or explicitly re-versioned in the roadmap;
- every exposed client and realm property has semantic validation, risk, policy, verification, and tests;
- real integration coverage and tested product versions are reported accurately;
- no secret leakage or cross-target access is found;
- final backend and frontend validation passes;
- limitations and compatibility documentation are current.

## Current implementation status and limitations

- Typed redirect URI and Web Origin set replacement is implemented through shared REST/MCP application services.
- Validation currently accepts exact absolute HTTP(S) redirect URIs, path-suffix `/*` redirect wildcards, and loopback HTTP. Relative redirect URIs are rejected.
- Web Origins accept exact HTTP(S) origins and the Keycloak `+` sentinel; the sentinel remains `NOT VERIFIED` against the supported live-version matrix.
- Scalar client updates for `name`, `description`, and `pkceCodeChallengeMethod` remain available from the 0.8 proof of concept.
- Client security/flow settings, client creation/enable/disable, and realm administration are not implemented.
- The opt-in controlled-write IT uses a uniquely named client in the imported disposable realm, enforces an exact loopback target guard, executes plan → approve → apply → read-back → restore, verifies fixture removal, and covers stale-plan rejection.
- Community Keycloak 26.7.1 is verified by the disposable IT; RHBK and Web Origin `+` semantics remain `NOT VERIFIED`.
- Admin API v2 is not used.

## Out of scope

- delete realm or client;
- passwords, client-secret retrieval, secret rotation, private keys, or IdP secrets;
- arbitrary client/realm attributes or complete representation payloads;
- raw Admin REST or arbitrary JSON mutation tools;
- fleet reporting, target onboarding, and fleet posture (0.8.2);
- platform authorization and governance (0.8.3);
- users, groups, roles, and role mappings (0.8.4);
- authentication-flow editing/bindings, client scopes, and protocol mappers (0.8.5);
- identity providers and advanced realm configuration (0.8.6);
- automatic remediation;
- a full Keycloak administration console in the Web UI.
