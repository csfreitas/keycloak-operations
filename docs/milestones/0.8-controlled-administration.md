## Objective

Introduce a safe, auditable and policy-controlled foundation for modifying Keycloak and Red Hat build of Keycloak environments.

The platform currently follows a predominantly read-only operational model:

```text
Discover
   ↓
Observe
   ↓
Assess
   ↓
Explain
```

This milestone extends that lifecycle to:

```text
Discover
   ↓
Assess
   ↓
Plan
   ↓
Review
   ↓
Approve
   ↓
Apply
   ↓
Verify
   ↓
Audit
```

The goal is not to expose the Keycloak Admin REST API directly through MCP.

The goal is to provide controlled semantic administration capabilities that can later support realm, client, user, group, role, authentication flow, client scope and identity provider management.

---

## Architectural Principle

AI must never receive unrestricted write access to Keycloak.

The write architecture MUST be:

```text
User / AI
    |
    v
Semantic Change Request
    |
    v
Change Planning
    |
    +--> Current State
    +--> Desired State
    +--> Diff
    +--> Risk Classification
    +--> Policy Evaluation
    |
    v
Change Plan
    |
    v
Explicit Approval
    |
    v
Apply
    |
    v
Read-back Verification
    |
    v
Audit
```

The LLM may request and explain changes.

It MUST NOT bypass:

* target authorization;
* policy evaluation;
* approval requirements;
* validation;
* verification;
* audit.

# Scope

## Change Management Domain Model

Introduce a normalized change model.

Suggested concepts:

```text
ChangeRequest
ChangePlan
ChangeOperation
ChangeDiff
ChangeRisk
ChangePolicyDecision
ChangeApproval
ChangeExecution
ChangeVerification
ChangeResult
```

The concrete implementation may adapt these names to existing project conventions.

---

## Change Request

A ChangeRequest represents desired state, not a raw HTTP operation.

Example:

```json
{
  "targetId": "customer-a-prd",
  "resourceType": "CLIENT",
  "resourceId": "portal-web",
  "operation": "UPDATE",
  "desiredState": {
    "pkceCodeChallengeMethod": "S256"
  }
}
```

It MUST NOT contain:

* arbitrary URLs;
* arbitrary REST paths;
* raw HTTP methods;
* bearer tokens;
* passwords;
* client secrets.

---

## Change Plan

Before applying a write, the platform must produce a plan.

Example:

```json
{
  "changeId": "chg-12345",
  "targetId": "customer-a-prd",
  "resourceType": "CLIENT",
  "resourceId": "portal-web",
  "operation": "UPDATE",
  "risk": "MEDIUM",
  "requiresApproval": true,
  "changes": [
    {
      "property": "pkceCodeChallengeMethod",
      "before": null,
      "after": "S256"
    }
  ]
}
```

The plan must be based on current state read from the target.

---

## Diff Model

The platform must provide a normalized diff:

```text
ADDED
REMOVED
CHANGED
UNCHANGED
```

A diff must never expose sensitive values.

For sensitive properties, use representations such as:

```text
********
CONFIGURED
NOT_CONFIGURED
CHANGED
```

Never expose the actual value.

---

## Risk Classification

Introduce deterministic risk classification.

Suggested levels:

```text
LOW
MEDIUM
HIGH
CRITICAL
```

Examples:

```text
LOW
Change client display metadata

MEDIUM
Enable PKCE requirement

HIGH
Modify authentication flow binding

CRITICAL
Potentially destructive or environment-wide security change
```

Risk classification must not be decided by the LLM.

---

# Authorization Model

Introduce explicit administration permissions.

Suggested permissions:

```text
READ
ASSESS
PLAN
WRITE
ADMIN
```

Definitions:

```text
READ
Read target configuration.

ASSESS
Execute assessments and health checks.

PLAN
Generate proposed changes and diffs.

WRITE
Apply approved non-administrative changes.

ADMIN
Apply high-impact administrative changes.
```

Authorization must remain target-aware.

Authorization to modify Target A must not grant access to Target B.

---

# Environment Policies

Introduce environment-sensitive change policies.

Suggested default model:

```text
DEV
READ      ALLOW
ASSESS    ALLOW
PLAN      ALLOW
WRITE     ALLOW_WITH_POLICY
ADMIN     APPROVAL_REQUIRED

TEST/HML
READ      ALLOW
ASSESS    ALLOW
PLAN      ALLOW
WRITE     APPROVAL_REQUIRED
ADMIN     APPROVAL_REQUIRED

PRD
READ      ALLOW
ASSESS    ALLOW
PLAN      ALLOW
WRITE     APPROVAL_REQUIRED
ADMIN     APPROVAL_REQUIRED
DELETE    DENY_BY_DEFAULT
```

These are policy defaults, not hardcoded universal behavior.

Policies must be configurable.

---

# Approval

A change requiring approval MUST NOT be applicable only because the same MCP interaction created the plan.

The system must distinguish:

```text
PLAN
```

from:

```text
APPROVAL
```

and:

```text
APPLY
```

Suggested lifecycle:

```text
DRAFT
PLANNED
WAITING_APPROVAL
APPROVED
APPLYING
APPLIED
VERIFIED
FAILED
REJECTED
EXPIRED
```

The exact state model may be adapted.

---

# Approval Integrity

Approval must be associated with:

* change ID;
* target ID;
* exact proposed change;
* plan hash/version;
* approver identity when available;
* approval timestamp.

If the plan changes after approval, the previous approval must become invalid.

This prevents:

```text
approve change A
        ↓
modify plan into change B
        ↓
apply using approval A
```

---

# Plan Hash

Generate a deterministic fingerprint/hash for the approved plan.

The Apply operation must verify that the plan being applied matches the approved fingerprint.

---

# Apply

Apply must accept a previously created approved ChangePlan.

It must NOT accept arbitrary desired state directly when approval is required.

Conceptually:

```text
apply(changeId)
```

not:

```text
apply(targetId, arbitraryJson)
```

---

# Verification

Every successful write must be followed by read-back verification when technically possible.

Flow:

```text
Apply
   ↓
Keycloak Admin API
   ↓
Read Resource Again
   ↓
Compare Desired State
   ↓
VERIFIED / VERIFICATION_FAILED
```

HTTP success alone must not be treated as sufficient proof that desired state was reached.

---

# Audit

Every administration operation must generate audit information.

Include:

```text
changeId
targetId
resourceType
resourceId
operation
risk
policyDecision
approval status
actor when available
createdAt
approvedAt
appliedAt
verification status
result
```

Audit must not contain secret values.

---

# Persistence

Persist Change Management state in PostgreSQL.

Expected concepts:

```text
change_request
change_plan
change_operation
change_approval
change_execution
change_verification
```

The exact schema should follow existing persistence conventions.

Use Flyway migrations.

# Semantic Administration

This milestone must establish the architecture used by future administration tools.

Never introduce:

```text
keycloak_raw_request
keycloak_admin_request
keycloak_execute_rest
keycloak_execute_json
```

Future operations must be semantic.

Examples:

```text
keycloak_plan_create_realm
keycloak_plan_update_client
keycloak_plan_create_user
keycloak_plan_assign_role
```

---

# MCP Foundation Tools

Implement a small generic Change Management interface rather than every Keycloak write operation.

Suggested tools:

```text
keycloak_get_change
keycloak_list_changes
keycloak_approve_change
keycloak_reject_change
keycloak_apply_change
keycloak_verify_change
```

Planning operations may initially be demonstrated using a very small controlled resource set.

Do not expose arbitrary mutation payloads.

---

# REST API

Provide equivalent REST capabilities.

Suggested endpoints:

```text
GET  /api/v1/changes

GET  /api/v1/changes/{changeId}

POST /api/v1/changes/{changeId}/approve

POST /api/v1/changes/{changeId}/reject

POST /api/v1/changes/{changeId}/apply

POST /api/v1/changes/{changeId}/verify
```

Resource-specific planning endpoints will be introduced by the administration sub-milestones.

REST and MCP must share the same Application Services.

# Web UI Integration

If the Web UI exists, add only the necessary Change Management views.

Suggested:

```text
Changes
  ├── Pending approval
  ├── Approved
  ├── Applied
  ├── Failed
  └── History
```

Change detail should display:

```text
Target
Environment
Resource
Operation
Risk

Approval status
Apply status
Verification result
Audit timeline
```

Do not build the complete Keycloak administration UI in this milestone.

---

# Secret Handling

Secrets are explicitly protected.

This milestone MUST NOT expose:

* user passwords;
* client secrets;
* identity provider client secrets;
* private keys;
* access tokens;
* refresh tokens;
* credential values.

Sensitive fields must be:

```text
redacted
referenced indirectly
or handled by a future SecretProvider abstraction
```

Secret-setting workflows are outside the initial 0.8 foundation.

---

# Destructive Operations

Delete operations are OUT OF SCOPE for the initial 0.8 foundation.

Do not implement generic deletion.

Future destructive operations require:

* explicit requirements;
* high/critical risk;
* explicit authorization;
* explicit approval;
* resource-specific safeguards.

---

# Concurrency Protection

The platform must protect against stale plans.

Example:

```text
Plan created:
client redirectUris = A

Someone changes target:
redirectUris = B

Apply old plan
```

The system should detect that current state no longer matches the state on which the plan was based.

Result:

```text
CONFLICT
REPLAN_REQUIRED
```

Do not silently overwrite external changes.

---

# Idempotency

Apply operations should be idempotent where technically possible.

Repeated execution of the same approved operation must not unintentionally create duplicated resources or repeated mutations.

---

# Error Model

Extend domain errors with controlled administration failures such as:

```text
CHANGE_NOT_FOUND
CHANGE_NOT_APPROVED
CHANGE_EXPIRED
CHANGE_CONFLICT
CHANGE_ALREADY_APPLIED
POLICY_DENIED
APPROVAL_REQUIRED
APPROVAL_INVALID
VERIFICATION_FAILED
WRITE_NOT_SUPPORTED
```

Names may follow current ErrorCode conventions.

---

# Compatibility

Write operations must remain version/capability aware.

Do not assume a capability available in upstream Keycloak exists in the supported RHBK release.

Planning must fail safely with:

```text
UNSUPPORTED_CAPABILITY
```

when necessary.

---

# Initial Demonstration Operation

To validate the architecture, implement at least one low-risk semantic write operation end-to-end.

Recommended example:

```text
Update a non-sensitive client configuration property
```

or another controlled resource supported by existing Admin Client APIs.

The operation must demonstrate:

```text
PLAN
   ↓
DIFF
   ↓
RISK
   ↓
APPROVAL
   ↓
APPLY
   ↓
VERIFY
   ↓
AUDIT
```

Do not use a destructive operation as the first write implementation.

Change for Target A must never affect Target B.

# Acceptance Criteria

The milestone is complete when:

* ChangeRequest model exists.
* ChangePlan model exists.
* normalized safe diff exists.
* deterministic risk classification exists.
* policy evaluation exists.
* target-aware authorization exists.
* approval lifecycle exists.
* approval is bound to exact plan/version.
* apply requires an approved plan where policy requires approval.
* read-back verification exists.
* concurrency/stale-plan protection exists.
* audit persistence exists.
* no arbitrary Keycloak Admin REST write tool exists.
* secrets are not exposed.
* destructive operations remain disabled by default.
* MCP Change Management tools exist.
* equivalent REST endpoints exist.
* at least one semantic Keycloak mutation works end-to-end.
* multi-target isolation is tested.
* authorization is tested.
* approval integrity is tested.
* verification is tested.
* `mvn clean verify` passes.
* frontend tests pass if UI changes are included.

# Out of Scope

The initial 0.8 milestone does NOT attempt complete Keycloak administration.

Deferred to subsequent milestones:

```text
0.8.1
Realm & Client Administration

0.8.2
Users, Groups & Roles

0.8.3
Authentication Flows & Client Scopes

0.8.4
Identity Providers & Advanced Realm Configuration
```

Also out of scope:

* arbitrary Admin REST;
* arbitrary JSON mutation;
* raw HTTP tools;
* user password delivery;
* client secret retrieval;
* secret rotation;
* private-key handling;
* generic delete operations;
* automatic remediation without approval.
