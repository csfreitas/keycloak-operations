# Milestone 0.8.2 — Fleet Reporting & Target Onboarding

## Status

**PLANNED — on-demand report foundation implemented early; milestone not complete**

Delivery priority is now H1/D1–D5 in the [complete roadmap](../roadmap.md). Essential identity/target authorization is a prerequisite, not a subsequent task. Onboarding/retained-evidence replay and IAM/business analytics are not implied by the current on-demand report implementation.

## Objective

Make the Fleet Operations Console a practical single control plane for discovering, onboarding, assessing, and reporting the current posture of multiple Keycloak/RHBK environments without requiring source configuration edits.

## Requirements

`FR-REPORT-001` … `FR-REPORT-006`, `FR-AI-001` … `FR-AI-003`, `SEC-REPORT-001`, `SEC-AI-001`, `SEC-AI-002`, `NFR-REPORT-001`, `NFR-AI-001`, `NFR-ISO-001`, and the existing target/inventory/health/assessment requirements.

## Scope

- persisted target onboarding and safe configuration lifecycle;
- target connection and capability validation;
- per-target on-demand operations report;
- fleet posture summary and drill-down;
- report history/export with provenance;
- OpenShift and Kubernetes collector coverage surfaced explicitly;
- operator-visible `PARTIAL`, `FAILED`, `SKIPPED`, `NOT IMPLEMENTED`, and `NOT VERIFIED` states;
- AI-agent consumption through compact semantic MCP tools;
- Web UI report generation, view, and export.

The first on-demand `OperationsReportService`, REST endpoint, MCP tool, and minimal per-target Web UI report view are an early foundation only. They do not complete onboarding, history, fleet aggregation, or live compatibility verification.

## Architecture changes

See [`../architecture/operations-reporting.md`](../architecture/operations-reporting.md) and [`../architecture/ai-assisted-operations.md`](../architecture/ai-assisted-operations.md).

Target onboarding must store credential references only. It must validate reachability/capabilities without returning credentials and must not let callers provide arbitrary runtime endpoints to operational tools after registration.

## Security

- authorization is target-scoped;
- reports and persisted onboarding metadata are sanitized;
- Kubernetes Secret contents and unrestricted environment variables are excluded;
- AI does not bypass semantic contracts, read-only mode, policy, or approval;
- unsupported platform collectors do not fabricate evidence.

## Testing

- REST/MCP delegation to the shared report service;
- section-level partial degradation;
- separation of report completeness, health, and assessment status;
- redaction of structured and Markdown output;
- target and credential isolation;
- onboarding validation and rollback;
- persisted report provenance and export;
- UI accessibility and error/partial-state behavior;
- opt-in live Keycloak and RHBK runs with OpenShift/Kubernetes where available.

## Acceptance criteria

- Operators can register and validate a target without editing application source or exposing credentials.
- A report can be generated from REST, MCP, and the Web UI using the same application service.
- The report identifies target product, runtime evidence, health, assessment, findings, and performance availability.
- Partial or unsupported providers are visible and never converted to PASS or zero.
- Fleet posture links to target report evidence and timestamps.
- Automated validation passes; skipped live integrations are reported as skipped.

## Known limitations

VM and Docker collectors do not currently exist. Their coverage remains `NOT IMPLEMENTED` until separately designed, secured, and tested.

## Out of scope

- automatic remediation;
- arbitrary shell, `kubectl`, `oc`, Admin REST, or PromQL;
- broad realm/user/flow/IdP administration;
- notification delivery and schedules (0.9).

## Next milestone

Complete the presentation trust/document gates; full governance and semantic administration remain P2, with continuous observation/IAM analytics in P1 and isolated SPI assurance in P3.
